## 陷阱

⚠️⚠️⚠️ **【2026-06-08更新】持仓名单确认优先于成本确认 — 先确认"有什么标的"再确认"成本对不对"**

   **问题本质：** 前几次触雷是"成本数据错了但标的对了"。本次触雷是"标的名单就错了"——memory中标注了芯片/AI "已止盈"，我以为它们已清仓，实际上用户仍持有。这是比成本错误更严重的底层数据错误。

   **根源分析：** memory中的"完整持仓"字符串是用户某天一次性输入的快照，之后实际持仓可能已变化。特别地，"已止盈/之前止盈"在用户语境中**≠"已清仓"**。在A股投资语境中，"止盈"通常指**部分卖出锁定利润**（降低持仓成本），而不是全部清仓。用户说"芯片ETF 11400股 赚8040元 之前止盈"意味着：我在这笔交易上已经赚了8040元（已通过卖出部分股票锁定），但剩余仓位继续持有。成本从原始值降到了当前值。
   
   **关键语义映射：**
   | 用户说的 | 实际含义 | 动作 |
   |---------|---------|------|
   | "之前止盈" | 已部分卖出锁定利润，仓位继续持有 | 保留在监控标的范围，使用新成本 |
   | "已清仓" / "卖完了" | 已全部卖出 | 从监控标的范围移除 |
   | "止损了部分" | 部分卖出止损，剩余继续 | 保留但更新成本 |

   **持仓新鲜度验证机制：**
   
   第1步：**查脚本COST_PRICE字典 → 确定活跃持仓** — `morning_check.py`等监控脚本中的`COST_PRICE`字典维护当日的追踪列表。脚本中有成本记录的标的 = 当前活跃持仓。这个比memory中的"完整持仓"字符串更可信（脚本每天跑，memory可能几周没更新）。

   **【新增】用户说"早盘分析"或"早盘"时 → 直接运行morning_check.py并输出其报告格式。** 不要重新解释数据，不要用自己的分析框架覆盖，脚本输出就是最终报告。用户确认脚本数据正确后，再根据后续发问做深度分析。
   
   第2步：**对比memory持仓 vs 脚本COST_PRICE** — 两者应一致。不一致时以脚本为准（脚本有但memory无 → 用户加仓；memory有但脚本无 → 可能已清仓）。特别注意morning_check.py中的COST_PRICE是**每日读取的最新成本**，且包含完整的6-7个标的追踪列表；而memory中的"完整持仓"字符串可能包含过时的"已止盈"标注。
   
   第3步：**如果用户说"不对"/"我给你过最新的" → 停，直接问用户要当前持仓** — 不要试图拼凑历史session。给一个简单的表头让用户填空：
   ```
   当前持仓（名称、代码、股数、成本价）：
   1.
   2.
   ```
   **不要绕圈道歉，不要翻来覆去解释为什么用错了数据。问一次，等回复。**
   
   **执行检查清单（做持仓分析前必须过一遍）：**
   ```
   □ 从监控标的表（上方）确认活跃标的范围
   □ 从脚本COST_PRICE确认每个标的的成本
   □ 对比memory持仓字符串验证一致性
   □ 如持仓数据比最近一次会话早→主动确认
   ```

1. **⚡⚡⚡【强制拦截·升级版】持仓成本三步确认法 — 未确认不得输出浮盈** 

   **问题根源：** 过去三次触雷（建行/军工/AI芯片成本全错）都源于同一个模式——我读取了memory，但memory中的数据本身就是旧的。单纯"查memory"不够，需要主动输出让用户确认。

   **三步确认法（不可跳过）：**
   
   **第1步：从memory读取** — 调 `memory(action='list')` 获取 `memory` 中的`COST_NAV`记录
   
   **第2步：主动输出让用户确认** — 在输出任何浮盈/浮亏前，先给出当前已知的成本版本：
   ```
   当前memory中的成本记录：
   AI ETF 0.5138 × 9200股  |  芯片ETF 0.4527 × 11400股
   建行 <cost>  |  创新药 0.928(原)+0.790(新)
   
   这些成本是否正确？如有变更请告诉我。
   ```
   **特别是当用户第一次询问某个标的的加仓/减仓时，必须先过这步确认。**
   
   **第3步：用户确认后才输出浮盈分析** — 如果用户纠正，立即更新memory后重算
   
   **禁止行为：**
   - ❌ 不得在未确认成本的情况下直接输出"浮盈仅+X%"
   - ❌ 不得使用conversation历史中的旧成本（用户可能已止盈）
   - ❌ 不得使用脚本默认值（脚本中的COST_NAV是初始建仓成本，经多次操作已失效）

   **历史错误（每次触雷都是同一种模式）：**
   - 2026-06-02：AI/芯片成本用了止盈前的1.105/1.020（实际0.5138/0.4527），导致输出"浮盈薄不适合加仓"的错误结论
   - 2026-06-01：个股成本应以用户确认值为准，勿用过期默认值
   - 2026-06-01：军工成本0.78→实际1.670

6. **⚡ 脚本路径陷阱（Cron vs 交互模式）** — 两个场景路径解析不同：
   - **Cron 模式**（`no_agent: true`）：`script` 字段使用**相对路径**时，解析基准是 `~/.hermes/profiles/stunner/scripts/`，而不是 skill 自身的 `scripts/` 目录。部署脚本时**必须**同时将副本放入该路径，否则 cron 触发时报 `error`（找不到脚本文件）。三步部署法：
   ```bash
   mkdir -p ~/.hermes/profiles/stunner/scripts/
   cp <skill-dir>/scripts/*.py ~/.hermes/profiles/stunner/scripts/
   ```
   每次新增或修改脚本后都要重新 cp。脚本在 skill 目录保留主副本用于开发和备用。
   - **交互模式**（手动调用）：由于 `$HERMES_HOME` 和 shell 解析路径的影响，`cd <skill-dir>/scripts/` 或相对路径可能失败（`No such file or directory`）。**必须使用绝对路径**调用：
   ```bash
   python3 /Users/user/.hermes/profiles/stunner/skills/data-science/a-share-daily-monitor/scripts/morning_check.py
   ```
   `$HERMES_HOME` 指向 `~/.hermes/profiles/stunner` 时，这个绝对路径不受 `cd` 污染。
   ```bash
   mkdir -p ~/.hermes/profiles/stunner/scripts/
   cp <skill-dir>/scripts/*.py ~/.hermes/profiles/stunner/scripts/
   cp <skill-dir>/scripts/run_*.sh ~/.hermes/profiles/stunner/scripts/
   ```
   每次新增或修改脚本后都要重新 cp（包括 `.py` 和 `.sh`）。脚本在 skill 目录保留主副本用于开发和备用。

   **2026-06-03 教训：** 空文件检查只查了 `.py`，但 `run_morning.sh` 在 skill 目录存在、cron 执行目录却没有——导致早盘 cron 挂起但无人发现。**两种文件类型都必须同步。**

11. **⚡ 一次性Cron提醒可能不抵达用户会话** — 通过 `cronjob(action='create', schedule='ISO_timestamp')` 创建的「一次性提醒」job，如果 `deliver='origin'` 可能投递到微信/groups等非当前会话渠道；如果 `deliver='local'` 则只保存不发送，用户不会收到任何通知。对于尾盘操作提醒这种「定时call我」的需求，不要用 cron，而是在当前会话用 terminal(background=true) + notify_on_complete 模式：`sleep 1800; echo '到时间了'`。或者在当前会话告诉用户「你到时间来找我，我数据已经准备好了」。

eps_2026 = 1.32  # 均值
# 用当前PE或行业平均PE估算
pe_current = 7.9
target_conservative = eps_2026 * 7.0
target_neutral = eps_2026 * 7.5
target_optimistic = eps_2026 * 8.0
```

31. **不要将「基本面做多逻辑」与「短期战术时机」混为一谈** — 当用户问"XX基本面很好/政策支持，能不能加仓"时，这是两个独立问题。必须先检查：(1)仓位是否已过重？(2)浮亏是否已触止损线？(3)近期是否有明确催化剂？不能因为"长期逻辑成立"就跳过风险检查。输出格式：先给止损检查结果，再给加仓判断。

32. **⚡ 同名不同ETF代码混淆陷阱
    - 持仓创新药代码是 **589720**（见监控标的表），非159992
    - 任何时候用户说"XX回升了/跳水了"，先核对查询的代码是否与持仓表一致再请求新浪接口
    - 预防方案：查询前看一眼监控标的表，对照代码再查

33. **⚡ 观察型仓位与进攻型仓位不可混为一谈** — 当用户询问观察型仓位（如创新药589720）的加仓问题时，即使标的浮亏很大，也不等同于进攻型仓位的止损。观察仓的定位是"小仓位验证逻辑"，绝对金额小（占总资产~2%），核心看的是催化剂的兑现而不是短期价格。因此：
    - 不应用进攻型仓位的硬止损规则去催促用户立即止损
    - 不应在用户表达"社保基金越跌越买、认同长线逻辑"后，依然机械输出"规则要清仓"
    - 应尊重用户对该标的的独立判断逻辑（政策面、基本面、资金面），不越俎代庖
    - 持仓创新药代码是 **589720**（见监控标的表），非159992

34. **⚡ 用户主动报新成本 → 立即更新memory和脚本，不验证不追问** — 2026-06-09用户说\"我还有200股的高能环境，成本13.59\"（此前记录为13.69）。这种情况下用户已经主动纠错，直接更新memory中的成本记录，并记入监控标的表。**不需要再拉行情反推验证，不需要问\"你确定吗\"。** 用户主动报的数据就是权威数据。

```python
# 用户说红利ETF浮盈是-1.5%（不是memory中的-6.7%）
current_price = 0.618  # 新浪实时价
real_pnl = -1.5       # 用户纠正的浮盈
real_cost = current_price / (1 + real_pnl / 100)
# real_cost = 0.618 / (1 - 0.015) = 0.6274
```

反推后立即更新memory中的成本记录。**不要先道歉再查数据**——先拿数据算出来，再认错+更新+翻篇。

35. **⚡ 持仓股票的一手金额门槛检查** — 当推荐个股做卫星仓位增强时，必须先拉实时价算一手（100股）价格。像中际旭创1192元/股（一手12万）、北方华创603元/股（一手6万）这种标的，对卫星仓位来说门槛太高。必须在一开始确认门槛是否匹配用户资金量。

36. **⚡「前低博反弹」操作模式 — 不同于传统加仓买点** —
    
    当用户在下跌趋势中主动说「XX新低，博一下前低反弹」（如2026-06-02创新药0.790加仓1200股），这是**逆向操作模式**，不同于场景D的回踩均线加仓：
    
    **特征：**
    - 用户主动判断价格超跌、赔率够好，愿意承担短期风险
    - 仓位极小（1200股≈不到1000元），绝对金额可控
    - 用户不指望反弹后长期持有，而是赌一个技术性反弹就跑
    
    **处理方式（不要试图说服用户不要博）：**
    - 承认用户的判断逻辑（前低有支撑）
    - 帮用户设独立止损线（单独按新仓成本计算-5%/-8%/-10%）
    - 记录新仓位不混入原仓成本
    - 跟踪该仓位是否按预期反弹——如果不反弹反而继续下跌，在止损线触发时提醒
    
    **核心区别：**
    - 场景D加仓 = 旧仓浮盈厚、回调到技术支撑、均线系统向上
    - 博前低 = 旧仓浮亏深、下跌趋势中、靠前低支撑赌反弹

37. **⚡ 邮件密码不要写进公开仓库** — 曾有人用 base64 把 SMTP 密码「藏」在脚本里绕过脱敏扫描，但公开仓库里 base64 **仍可解码**。正确做法：只用环境变量（`SMTP_PASSWORD` 等），见 `scripts/email_wrapper.py`；泄露后立刻作废邮箱应用密码。

38. **脚本硬编码成本 vs 真实成本脱节** — 三个 cron 脚本应统一从 `portfolio.local.json` 读成本；不要在多个 `.py` 里各维护一份字典。改仓后只改 JSON，并跑一遍 morning/pre_close 确认浮盈。

39. **⚡ Cron 投递 deliver 目标格式验证陷阱** — 设置 cron 的 deliver 字段时，目标标识符必须匹配 `send_message(action='list')` 返回的注册平台目标，不能使用任意邮箱地址或猜测的格式。

   **2026-06-03 教训：** 我将早盘 cron 的 deliver 设为 `email:[redacted-email]`（认为这是邮箱地址格式），但 `send_message(list)` 返回的邮箱目标是 `email:user`。直接使用邮箱字符串导致投递可能无法路由到正确渠道。

   **正确做法（三步确认法）：**
   1. 调用 `send_message(action='list')` 查看所有已注册的投递目标
   2. 从返回列表中选取正确的 platform:id 格式（如 `email:user`、`weixin:o9cq8...`）
   3. 将确切的 target 字符串填入 cron deliver 字段

   **不安全的做法：**
   - ❌ 猜测邮箱地址（`email:xxxx@gmail.com`）
   - ❌ 假设微信ID就是微信号（需要 `send_message(list)` 返回的注册ID）
   - ❌ 使用 bare platform（如 `email`）而不指定目标ID——除非确实是发送到home channel

   **备注：** email 投递时，`send_message(list)` 返回的 `email:user` 不是用户输入的那个邮件地址，而是 Hermes 根据邮件 Gateway 配置注册的内部标识符。不要试图反推或用其他格式替代。

### ⚡ 场景T：累进阈值法 — 单边下跌行情中的DCA优化（2026-07-21新增）

**起源：** 2026-07-17至7/21一周内芯片从最高点1.589跌到最低1.169（-26.4%），科创50跌-22%。原-5%单日阈值在单边下跌行情中一周触发4次，7月额度第2周就打光了。用户指出「跌5%就加，不是傻子吗」。

**累进阈值规则：** 根据科创50从当月最高点的累计跌幅，动态调整DCA单日触发阈值。

| 科创50当月累计跌幅 | 单日DCA阈值 | 适用场景 |
|:------------------:|:----------:|:---------|
| < 10% | **-5%（不变）** | 正常回调期 |
| 10% ~ 15% | **-7%** | 深度回调期 |
| > 15% | **-10%** | 恐慌区 |

**执行逻辑：**
1. 月初记录科创50当月最高收盘价（或从morning_check脚本读取）
2. 每日计算科创50当月累计跌幅 = (当前价/当月最高价 - 1) × 100
3. 根据累计跌幅确定当前DCA阈值
4. 将该阈值用于所有品种的单日触发检查

**累计触发阈值不变**（AI -5% / 芯片 -6% / 军工 -5% / 创新药 -6%），因为累计触发已经在考量「已经跌了多少」了，不需要再套一层累进。

**回测效果（2026年7月）：**
- 7/10~7/14（科创50跌<10%）：-5%阈值不变 → 3次触发 ✅ 合理
- 7/16~7/17（科创50跌10-15%）：-7%阈值 → 0次触发（实际最大-5.98%<7%）
- 7/21（科创50跌>15%）：-10%阈值 → 0次触发
- **效果：从一周触发4次降到3次，下旬节省了额度**

详情见 `references/dip-dca-progressive-threshold.md`

### ⚡ 场景U：护盘行情分析 — 上证50涨+科技跌的极端分化

- 上证50 / 建行 / 红利涨 → 护盘资金拉权重
- 科创50 / 芯片 / AI跌 → 科技被砸
- 上证指数涨跌幅在±1%内（指数被权重稳住了）
- 中证500、中小100跟跌（中小盘没人管）

**诊断框架：**

| 检查项 | 护盘特征 | 非护盘特征 |
|:------|:--------|:----------|
| 上证50 vs 科创50 | 上证50明显强于科创50（差值>2%） | 同步涨跌 |
| 建行/红利走势 | 涨 | 跟跌或平 |
| 上证指数 | 小涨小跌（-1%~+1%） | 同步于真实情绪 |

- 护盘期间不追权重（追了就接盘）
- 科技持仓不动，等护盘资金耗尽了科技自然见底
- 护盘不是见底信号，科创50放量止跌才是

## 专项场景E：前低博反弹——新仓追踪框架

当用户说"加了XX股在X.XX"（博前低反弹），立即启动追踪：

**第一步：记录新仓参数**
- 标的、股数、买入价、时间
- 更新memory中的持仓记录

**第二步：设置止损参考线（用户心理止损，非强制规则）**
- -5% / -8% / -10% 三档，基于新仓独自的成本
- 注意区别于原持仓的硬止损线——新仓是新赌注

**第三步：后续报告中的仓位分离**
- 原仓浮盈/亏（用原成本算）
- 新仓浮盈/亏（用新成本算）
- 分开列示，不要混为一谈

**第四步：收盘后评估**
- 新仓价是否守住前低？→ 博成功了
- 新仓价再次破前低？→ 博失败了
- 和标的整体趋势对比（是独立反弹还是被板块拖着走）
